## Smart Contract Architecture

### Contract Inheritance & Interfaces

```
CertifyRegistry  (single registry — ZKPCertify removed)
├── AccessControl (OpenZeppelin)
│   └── Role-based permissions (ISSUER_ADMIN_ROLE, DEFAULT_ADMIN_ROLE)
├── Events (CertificateIssued, MemberDecision, ZKVerified, IssuerRemoved, …)
├── Replay protection (usedProofs mapping)
└── Verifier registry: mapping(predicateId → IGroth16Verifier)

└── verifyProof(a, b, c, uint[3]) → Groth16 proof validation (per circuit)
```

### CertifyRegistry Contract

**State Variables:**

```solidity
mapping(address issuer => bool) registeredIssuers;
mapping(address issuer => mapping(address holder => MemberRequest)) memberRequests;
mapping(uint256 certificateId => Certificate) certificates;
mapping(address holder => uint256[]) _holderCertificates;
mapping(address issuer => uint256[]) _issuerCertificates;
mapping(uint256 certificateId => Disclosure[]) _disclosures;

mapping(bytes32 proofHash => bool used) usedProofs; // replay protection

// One verifier per predicate circuit (PREDICATE_RANGE/EQUALITY/MEMBERSHIP).
mapping(bytes32 predicateId => IGroth16Verifier) verifiers;
uint256 private _certificateIdTracker;
```

**Key Functions:**

```solidity
// Membership (issuer)
function manageMember(address holder, bool approve)
function getIssuerCertificates(address issuer)

// Holder flows
function requestMembership(address issuer)
function shareCertificate(uint256 certificateId, address verifier, bytes32 queryHash, string calldata encryptedPayloadCid)
function getHolderCertificates(address holder)
function getDisclosures(uint256 certificateId)

// Certificate lifecycle
function issueCertificate(address holder, string calldata metadataCid, bytes32 metadataCommitment, bytes32 schemaId)
function setCertificateStatus(uint256 certificateId, CertificateStatus status)

// Admin: manage issuers + register a predicate's verifier
function registerIssuer(address issuer)
function removeIssuer(address issuer)
function setVerifier(bytes32 predicateId, address verifier)

// Verifier — one entry point per predicate, all uint[3] pubSignals
function verifyRangeProof(id, a, b, c, [root, keyHash, threshold])
function verifyEqualityProof(id, a, b, c, [root, keyHash, value])
function verifyMembershipProof(id, a, b, c, [root, keyHash, setRoot])
```

**Shared verification (internal `_verify(predicateId, …)`), in order:**

1. `verifiers[predicateId]` is set (else revert "unknown predicate").
2. Certificate is `Active`.
3. `pubSignals[0]` (the circuit's Merkle root output) equals
   `cert.metadataCommitment` — binds the anonymous proof to this certificate.
4. `keccak256(abi.encode(predicateId,a,b,c,pubSignals))` not in `usedProofs` — replay guard.
5. The predicate's verifier `verifyProof(...)` returns true.
6. Emits `ZKVerified(certificateId, msg.sender, predicateId, keyHash, param)`.

**Security Features:**

- ✅ Immutable verifier address (set in constructor, cannot be swapped)
- ✅ Access control via `onlyIssuer` / `AccessControl` roles
- ✅ Commitment binding (proof tied to a specific certificate)
- ✅ Proof replay protection (`usedProofs` hash tracking)
- ✅ Input validation (non-zero holder/commitment, non-empty CID)

> Note: the previous parallel `ZKPCertify` contract has been removed — the
> registry is now the single source of truth.

## ZKP System

A credential is a set of claims committed as a Merkle root
(`leaf = Poseidon(keyHash, value, salt)`, `node = Poseidon(left, right)`, depth 4;
shared template in `zk/circuits/merkle.circom`). Three predicate circuits prove a
statement about ONE claim while hiding the rest; all output `root` (bound on-chain
to `cert.metadataCommitment`) and take `keyHash` public, so every on-chain verifier
shares the same `uint[3]` signature `[root, keyHash, param]`.

| Circuit | Proves | `param` (pubSignals[2]) |
|---|---|---|
| `range.circom` | `value ≥ threshold` (`GreaterEqThan`, 32-bit; also expiry) | threshold |
| `equality.circom` | `value == X` (Merkle inclusion; value revealed) | value |
| `membership.circom` | `value ∈ set` (credential + set Merkle inclusion, which one hidden) | setRoot |

### The range circuit

**File:** `zk/circuits/range.circom`

A credential is a set of numeric claims committed as a Merkle root
(`leaf = Poseidon(keyHash, value, salt)`, `node = Poseidon(left, right)`, depth 4).
The circuit proves that ONE claim's value satisfies `value >= threshold` and that
it belongs to the credential whose root is the public output — revealing neither
the value nor the other claims.

```circom
pragma circom 2.0.0;
include "circomlib/circuits/poseidon.circom";
include "circomlib/circuits/comparators.circom";
include "circomlib/circuits/bitify.circom";

template Range(levels) {
    signal input value;               // private, scaled integer
    signal input salt;                // private blinding
    signal input pathElements[levels];// private Merkle path
    signal input pathIndices[levels];
    signal input keyHash;             // public — which claim
    signal input threshold;           // public — the minimum
    signal output root;               // public — Merkle root

    // leaf = Poseidon(keyHash, value, salt); recompute root via the path.
    // (DualMux + Poseidon(2) per level — see the source.)

    // Range-bound the value, then enforce value >= threshold.
    component vbits = Num2Bits(16);
    vbits.in <== value;
    component ge = GreaterEqThan(16);
    ge.in[0] <== value;
    ge.in[1] <== threshold;
    ge.out === 1;
}

component main {public [keyHash, threshold]} = Range(4);
```

**Circuit Logic:**

1. **Merkle inclusion**: recomputes the root from `leaf + path`; the on-chain
   check `root == cert.metadataCommitment` binds the proof to the credential.

2. **Enforced range**: `GreaterEqThan(16)` + `ge.out === 1` force
   `value >= threshold`. (The *original* GPA circuit only assigned
   `diff <== actualGpa - minGpa` and never constrained it, so any value passed —
   that soundness hole is fixed here.)

Because the predicate is generic over `(keyHash, value, threshold)`, the same
circuit proves GPA (diploma), score/level (competency), or any future numeric
claim — no new circuit per credential type.

**Public Signals Format** (snarkjs order: outputs, then public inputs):

```javascript
[
  root,       // pubSignals[0] - Merkle root; must equal cert.metadataCommitment
  keyHash,    // pubSignals[1] - which claim was proven (e.g. keyHash("gpa"))
  threshold   // pubSignals[2] - the minimum value proven
]
```

Build the circuit + keys + Solidity verifier with `cd zk && ./build.sh`.

### Trusted Setup

`zk/build.sh` runs the whole ceremony for all 3 circuits — it generates a dev
powers-of-tau (power 12) locally, then per circuit does groth16 setup +
contribute + export vkey + export Solidity verifier (renamed per circuit).
Dev entropy: fine for local/testnet, not mainnet.

```bash
npm run zk:build      # generates ptau, builds range/equality/membership
```

## Proof Generation & Verification

### Proof Generation Flow (Client-side)

```javascript
// 1. At issue time (issuer): commit the claims as a Merkle root.
//    buildCommitment scales values, generates a salt per claim, builds the tree.
const { rootHex, salts } = buildCommitment(schema, { gpa: 3.85 });
// salts (+ raw claim values) are stored in the IPFS metadata so the holder
// can prove later. metadataCommitment = rootHex.

// 2. At proof time (holder/verifier): pick a claim + threshold.
const proof = await generateRangeProof(schema, metadata, "gpa", 3.5);
//   internally builds circuit inputs:
//     value, salt, pathElements, pathIndices  (private)
//     keyHash = keyHash("gpa"), threshold      (public)
//   then groth16.fullProve(input, "/zk/range.wasm", "/zk/range.zkey")

// 3. Public signals visible to the verifier
proof.publicSignals = [
  root,       // 0: Merkle root (== cert.metadataCommitment)
  keyHash,    // 1: which claim (keyHash("gpa"))
  threshold   // 2: minimum value proven (350 = 3.5 ×100)
]
```

### Proof Verification Flow (On-chain)

```solidity
function verifyRangeProof(
    uint256 certificateId,
    uint[2] calldata a,
    uint[2][2] calldata b,
    uint[2] calldata c,
    uint[3] calldata pubSignals // [root, keyHash, threshold]
) external returns (bool) {
    Certificate memory cert = certificates[certificateId];

    // 1. Certificate must be active
    require(cert.status == CertificateStatus.Active, "inactive cert");

    // 2. Root binds the anonymous proof to THIS credential
    require(bytes32(pubSignals[0]) == cert.metadataCommitment, "commitment mismatch");

    // 3. Replay guard: a given proof is single-use
    bytes32 proofHash = keccak256(abi.encode(a, b, c, pubSignals));
    require(!usedProofs[proofHash], "proof already used");

    // 4. Verify Groth16 proof (which enforces value >= threshold in-circuit)
    require(verifiers[predicateId].verifyProof(a, b, c, pubSignals), "invalid proof");

    usedProofs[proofHash] = true;
    emit ZKVerified(certificateId, msg.sender, pubSignals[1], pubSignals[2]);
    return true;
}
```

> Note: verification is intentionally NOT restricted to the holder — anyone
> holding a valid proof (e.g. a verifier the holder shared with) can submit it.
> Privacy comes from the ZK proof, and binding from the commitment check.

### Security Measures

1. **Proof Replay Protection**
   - Each proof has unique `proofHash`
   - Once verified, same proof cannot be used again
   - Nonce in certificate prevents old proofs for new issues

2. **Commitment Verification**
   - Public signal must match stored metadata commitment
   - Ensures prover used correct metadata

3. **Holder Verification**
   - Only certificate holder can verify proof
   - Prevents impersonation

4. **Revocation Check**
   - Revoked certificates cannot be verified
   - Issuer can revoke anytime

## Design Decisions

### Why Groth16?

- ✅ Widely adopted ZKP scheme
- ✅ Constant proof size (~288 bytes)
- ✅ Fast verification (< 1ms on-chain)
- ✅ Well-supported by snarkjs ecosystem

### Why Circom for Circuit?

- ✅ Designed specifically for ZKP applications
- ✅ High-level constraint language (vs low-level)
- ✅ Good tooling with snarkjs
- ✅ Active community support

### Why a Single Registry (not two contracts)?

- The earlier design had two overlapping contracts (`CertifyRegistry` +
  `ZKPCertify`) with three mutually-incompatible verifier interfaces, none of
  which lined up. Consolidating into `CertifyRegistry` (issuer/membership/
  lifecycle/disclosure **and** ZK verification) removes that mismatch and gives
  the frontend a single source of truth.

### Why Poseidon Commitment (not keccak of JSON)?

- The circuit can reproduce the Merkle root of the claims cheaply in-circuit, so the
  on-chain commitment and the proven commitment actually match. A keccak of the
  metadata JSON cannot be recomputed inside the circuit, so it could never be
  bound by the proof (and the old issuer/circuit even hashed it two different
  ways — they never matched).

### Why Hash-Based Replay Protection?

- `usedProofs[keccak256(a,b,c,pubSignals)]` marks each proof single-use.
- The commitment already scopes a proof to one certificate, so a per-proof hash
  is sufficient and simpler than certificate nonces.

| Term | Definition |
|------|-----------|
| **Commitment** | Cryptographic hash binding prover to specific data |
